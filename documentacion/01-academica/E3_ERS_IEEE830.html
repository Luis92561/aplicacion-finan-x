1. Introducción

1.1 Propósito

Este documento especifica los requisitos de FINAN-X, un sistema de facturación y pagos con portal de autoservicio para el cliente. Está dirigido a:

  • El equipo de desarrollo, como contrato de lo que debe construirse.
  • El docente evaluador o un revisor externo, para verificar que lo entregado corresponde a lo especificado.
  • Un desarrollador futuro que reciba el proyecto, para entender qué hace y por qué.

Responde a la pregunta guía de la evidencia: ¿qué debe hacer exactamente el sistema y bajo qué condiciones debe funcionar?

1.2 Alcance

FINAN-X cubre el ciclo de venta y cobro de una empresa que factura a sus clientes:

Cliente → Pedido → Factura → Pago → (Nota de crédito si hay devolución)

El sistema ofrece dos áreas diferenciadas: un panel interno para el personal de la empresa (administrador, facturador, cajero y supervisor) y un portal del cliente para que cada cliente consulte y pague sus propias facturas.

Fuera de alcance

FINAN-X no es un sistema ERP. Quedan expresamente fuera: contabilidad general, gestión de inventario y stock, nómina, compras a proveedores, y la integración fiscal con la DIAN (el documento de factura es informativo, no tiene validez tributaria). Ver la sección 7, Restricciones.

2. Descripción general

2.1 Perspectiva del producto

FINAN-X es un producto independiente y autocontenido: se levanta con un solo comando y no depende de servicios externos. Se compone de tres piezas que se comunican por HTTP:

Navegador  →  Frontend (React)  →  API REST (Node/Express)  →  PostgreSQL 16

2.2 Funciones principales

Grupo de funcionesQué incluye
Autenticación y seguridadAcceso interno y de cliente, autoregistro, recuperación de contraseña con OTP, cierre de sesiones, control por roles.
ClientesAlta, edición, búsqueda, activar/inactivar y creación de la cuenta de portal.
ProductosCatálogo con precio, impuesto, unidad de medida y baja lógica.
PedidosCreación con líneas, cálculo de totales en el servidor, confirmación y cancelación.
FacturaciónEmisión desde un pedido, consulta, saldo, anulación con motivo y refacturación.
PagosRegistro con distintos medios, control de saldo y estado de pago automático.
Notas de créditoDevoluciones con motivo y anulación lógica.
ReportesResumen del negocio, facturación por rango, balance por cliente e historial.
AuditoríaRegistro y consulta de todas las operaciones sensibles.
Portal del clienteConsulta de saldo, compras, facturas, pagos, notas y datos propios, y pago en línea.

2.3 Usuarios del sistema

El sistema distingue cinco tipos de usuario. Los cuatro primeros son personal interno de la empresa y se reparten las tareas; el quinto es el cliente, que solo accede a su propia información.

RolQuién esQué puede hacerQué NO puede hacer

FacturadorÁrea comercialClientes, productos, pedidos, emisión y anulación de facturas, reportes, envío del estado financiero.Gestionar usuarios. Consultar la auditoría.
CajeroÁrea de cajaRegistrar pagos y notas de crédito, consultar facturas, clientes y pedidos.Gestionar usuarios, consultar la auditoría ni emitir facturas.
SupervisorÁrea de controlConsultar todo, reportes, balances e historial. Consultar la auditoría.Registrar pagos, emitir facturas ni gestionar usuarios.
ClienteCliente de la empresaVer y pagar sus propias facturas, consultar su saldo, sus compras, sus pagos y sus datos.Ver información de otros clientes, ni acceder al panel interno.

2.4 Entorno de operación

  • Servidor: cualquier equipo con Docker. Tres contenedores: PostgreSQL 16, la API en Node.js y el frontend servido por nginx.
  • Cliente: navegador web actual (Chrome, Edge, Firefox o Safari). No requiere instalación.
  • Base de datos: PostgreSQL 16 con un volumen persistente para los datos.

2.5 Restricciones de diseño y supuestos

TipoDescripción
TecnológicaEl frontend se desarrolla con React 18 + Vite; el backend con Node.js + Express; la base de datos es PostgreSQL 16.
De despliegueEl sistema se ejecuta en contenedores Docker orquestados con Docker Compose, sobre cualquier máquina con Docker instalado.
De entornoNode.js 20 o superior. El proyecto se ha probado con Node 24 y PostgreSQL 16.
LegalEl software se distribuye bajo licencia de uso; las dependencias de terceros conservan sus licencias (ver Evidencias 4 y 5).
De alcanceEl sistema no es un ERP: no incluye contabilidad general, inventario, nómina ni compras a proveedores. La facturación no tiene validez fiscal (no emite CUFE ni se integra con la DIAN).
De seguridadLa recuperación de contraseña por SMS o correo no envía mensajes reales en esta versión: el proveedor de mensajería queda como punto de extensión.
De integraciónEl código de pago en efectivo es una simulación: no se persiste ni se redime contra una pasarela real.
AcadémicaProyecto de la asignatura Integración de Aplicaciones. La variedad de roles y los límites de peticiones responden a fines didácticos.

Supuestos: el equipo dispone de Docker; el cliente final tiene acceso a un navegador; la entrega del OTP por SMS o correo se sustituye por el modo demostración mientras no se contrate un proveedor.

6. Reglas de negocio

Las reglas de negocio son las invariantes del sistema: condiciones que deben cumplirse siempre, independientemente de quién ejecute la operación o desde dónde. Se aplican en la base de datos y en la API, no solo en la interfaz.

IDReglaDónde se aplica
RN-01Un cliente no puede repetirse por tipo y número de identificación.Restricción UNIQUE + validación previa → 409.
RN-02Los importes de un pedido los calcula siempre el servidor a partir del precio del catálogo.El navegador nunca envía totales; el precio se lee de la base.
RN-03Un pago no puede superar el saldo pendiente.Validación contra la vista factura_saldo → 400.
RN-04El saldo de una factura no se almacena: se deriva de los pagos y las devoluciones.Vista factura_saldo.
RN-05Como mucho una factura activa por pedido; las anuladas se conservan como historial.Índice único parcial uq_factura_activa_por_pedido.
RN-06Solo se puede facturar un pedido confirmado.Validación de estado → 409.
RN-07Un pedido facturado no se puede modificar.El pedido pasa a FACTURADO y la edición exige BORRADOR → 409.
RN-08La anulación de facturas y notas de crédito es lógica y exige motivo.Se marca el estado y se guarda el motivo → 400 si falta.
RN-09No se puede anular una factura con pagos.Comprobación → 409.
RN-10Una nota de crédito no puede devolver más de lo pagado menos lo ya devuelto.Cálculo del disponible → 400/409.

RN-15El número completo de la tarjeta y el CVV nunca se almacenan.Validación que descarta esos campos antes de guardar.
